1. 이 문서는?

쉽게 말하면: 이미 macOS에서 완성해 쓰고 있는 도구를 Windows에서도 똑같이 쓰게 만드는 "이사 계획서"예요. 그대로 옮겨도 되는 짐(제품의 95%)과, 새 집에 맞춰 다시 만들어야 하는 부분(캡처 방식·좌표 규칙·설치 방법)을 구분해 정리했어요.

이 문서는 여기요!! Windows 버전의 작업계획서다. macOS판은 Phase 0~3이 완료되어 실사용(도그푸딩) 중이고, CapNote v1 스펙은 동결되어 있다. 따라서 이 문서는 그린필드 계획서가 아니라 이식(port) 계획서다 — 왜 이 설계가 Windows에서 더 유리한지(§3), 무엇이 그대로 가고(§4), 무엇을 새로 만들며(§5), 어떤 정책을 Windows에 맞게 개정하고(§6~7), 어떤 셸·배포를 선택하며(§8), 어떤 순서로 며칠 만에 하는지(§9~10), 무엇이 위험하고(§11), 착수 전에 무엇을 결정해야 하는지(§12)를 다룬다.

제품이 무엇인지·왜 필요한지·CapNote v1 문법·어노테이션 창 설계는 여기에 중복 기술하지 않는다 — plan.html §2~6이 단일 출처다. 이 문서는 Windows에서 달라지는 것만 다룬다.

이 계획서의 기술적 주장(캡처 API·플러그인 이슈·Claude Code 거동·DPI 규칙)은 2026-07-03에 공식 문서·GitHub 이슈 기준으로 조사·검증한 것이다. 착수 시점이 늦어지면 §11 리스크 9(외부 가정 결합)와 §12 미해결 질문을 재확인할 것.

문서 언어 정책: 산문은 한국어, 코드·CLI 명령·포맷 키워드는 영어. 수치·경로·단축키(CapNote v1, Alt+Shift+C, %USERPROFILE%\.capnote\, 14일/500개)는 모든 문서에서 동일하게 유지한다. 단 공유 수치 중 "1568px 단일 규칙"은 §6.2의 정책 개정 대상이다 — 개정이 확정되면 plan.html §1·§5와 CLAUDE.md의 해당 수치도 함께 개정한다(§12 결정 4).

2. 목표 — 같은 루프, 같은 포맷, 다른 OS

쉽게 말하면: Windows에서도 "단축키 → 찍고 → 표시하고 → 붙여넣기 한 번"이 macOS와 완전히 똑같이 되게 하는 게 목표예요. AI에게 보내는 편지 양식(CapNote)은 한 글자도 안 바꿔요.

목표는 단 하나다: macOS판의 제품 루프 — 전역 단축키 → 영역 선택 → 어노테이션(스마트 툴 3종·인라인 노트) → 원샷 커밋(번인 → 다운스케일 → PNG 저장 → CapNote 텍스트 클립보드 → 포커스 복귀) → 터미널 붙여넣기 — 를 Windows에서 동일한 체감 속도(마커 1개 ~5초, 3개 ~10초)로 재현한다.

불변식 5개의 지위 + Windows 보조 조항 2개

macOS판의 핵심 설계 불변식 5개(클립보드 텍스트 전용 · 단일 좌표계 = 저장 이미지 픽셀 · ≤1568px PNG · 다운스케일 후 번인 · 공유 번호 시퀀스, plan.html §2) 중 1·2·4·5는 Windows에서 무변경으로 성립하며 계속 위반 금지다. 불변식 3은 목적(모델이 보는 픽셀 = 텍스트 좌표, 정확히 1:1)은 불변이지만 수단(장변 ≤1568px 단일 규칙)이 리서치 결과 불충분한 것으로 판명되어 개정이 필요하다(§6.2) — 단, 이 계획서의 v1 범위(범용 프로필)는 현행 문언 안에서 동작하므로, 문언 개정(고해상도 프로필)은 §12 결정 4로 게이트한다. 불변식 개정은 이 문서가 단독 결정할 사안이 아니라 CLAUDE.md·plan.html 개정을 수반하는 사안이기 때문이다. 여기에 Windows 전용 보조 조항 2개를 추가한다:

  1. 모든 프로세스는 Per-Monitor DPI Awareness v2(PMv2). Tauri(tao)가 메인 프로세스에 기본 적용하지만, 캡처 헬퍼 등 별도 프로세스를 만든다면 그 프로세스도 PMv2를 선언해야 한다 — 미선언 프로세스는 좌표·화면 크기가 96dpi로 가상화되어 좌표계 불변식이 조용히 깨진다.
  2. 화면 지오메트리 계산은 Rust에서만. 모니터 물리 rect·scale factor는 Tauri Monitor API(Win32 GetDpiForMonitor)로 취득한다. WebView2의 JS 화면 API가 mixed-DPI 멀티모니터에서 잘못된 값을 반환하던 버그(MicrosoftEdge/WebView2Feedback#4826)는 런타임 147.0.3891.0(2026-03)에서 수정됐지만, 미갱신·고정 버전 런타임의 잔존 가능성과 웹뷰 화면 API의 일반적 mixed-DPI 신뢰성 한계를 고려해 심층 방어로 Rust 단독 지오메트리를 유지한다.

3. 왜 Windows에서 이 설계가 더 강한가

쉽게 말하면: Windows의 AI 터미널에서는 "그림 붙여넣기"가 더 헷갈려요(Ctrl+V가 아니라 Alt+V). 우리는 처음부터 그림을 클립보드에 안 넣는 방식이라, 이 헷갈림을 아예 우회해요 — macOS에서보다 장점이 더 커져요.

macOS판 설계의 출발점은 "Claude Code의 이미지 붙여넣기는 ⌘V가 아니라 Ctrl+V"라는 함정이었다(plan.html §3). Windows에서 이 함정은 사라지는 게 아니라 형태를 바꿔 존속한다: Windows Terminal이 Ctrl+V를 "텍스트 붙여넣기"로 먼저 소비하기 때문에, Claude Code의 이미지 붙여넣기는 Alt+V라는 더 비직관적인 키에 배정되어 있다(공식 interactive-mode 문서). 게다가 네이티브 Windows에서는 원시 비트맵 클립보드의 이미지 붙여넣기가 조용히 실패하는 사례가 반복 보고되어 있다(claude-code #32791 등).

즉 "번인 PNG는 파일로 저장하고, 클립보드에는 경로가 포함된 텍스트만 넣는다"(불변식 1)는 이 제품의 설계가 Windows에서는 표준 Ctrl+V 한 번으로 시각+의미 채널이 동시 도착하는 유일하게 안정적인 경로가 된다. 파일 경로 참조는 Claude Code 공식 문서가 명시한 이미지 전달 방법이기도 하다. 이식의 정당성이 곧 제품 차별점이다.

4. 무엇이 그대로 가고, 무엇이 바뀌나 — 플랫폼 대응표

쉽게 말하면: 이삿짐 목록이에요. "그대로" 줄이 압도적으로 많아요 — 제품의 알맹이(그림 그리는 화면과 편지 양식)는 원래부터 OS를 안 가리게 만들어 놨거든요.

macOS판 아키텍처가 "웹뷰 UI 95% + 얇은 Rust 셸"이었던 것이 여기서 회수된다. 어노테이터·번인 렌더러·사이드카(PNG 옆에 저장되는 CapNote 텍스트 사본)·히스토리·설정 UI·GC는 무수정 재사용이고, 다운스케일 파이프라인과 CapNote 인코더의 scale: 줄은 정책 개정 대상(§6)이며, 새로 만드는 것은 Rust 셸의 OS 접점과 캡처 UI다.

5. 캡처 방식 결정 — 자체 오버레이 (이 계획서의 최대 결정)

쉽게 말하면: macOS에서는 OS가 "화면 오려내기 도구"를 공짜로 빌려줬는데, Windows에는 빌려 쓸 만한 게 없어요. 그래서 화면을 통째로 찍어 얼려 놓고, 그 위에서 우리가 직접 만든 선택 화면으로 오려내는 방식(Flameshot·Snipaste가 쓰는 방식)으로 갑니다.

  • 캡처 엔진은 xcap (v0.9.x, 활발 유지보수 · Tauri 생태계에 tauri-plugin-screenshots 통합 사례 존재). 기본 GDI 경로 사용 — WGC의 노란 캡처 테두리(Windows 10에서 제거 불가)를 피한다. 프리즈 프레임 1장에는 GDI로 충분하며, 화질·차단 이슈 발견 시 wgc feature로 전환 여지를 남긴다.
  • 창 선택 모드(macOS Space 토글 대응)는 W3에서 오버레이 내부에 구현: xcap Window::all()(cloaked 필터·z-order 제공)로 창 목록 확보 → 호버 시 최상위 창 rect 하이라이트 → 클릭 스냅. 경계는 DwmGetWindowAttribute(DWMWA_EXTENDED_FRAME_BOUNDS)로 취득 — GetWindowRect는 보이지 않는 리사이즈 테두리(~8px)를 포함해 어긋난다. 이미 프리즈 프레임에서 crop하므로 별도 창 캡처(PrintWindow)는 불필요.
  • 권한 온보딩 트랙 삭제. Windows에는 TCC 대응물이 없어 GDI 캡처에 사용자 승인이 필요 없다. 단 Windows 11 설정의 "데스크톱 앱 스크린샷 허용" 토글이 Off인 경우를 대비해, 캡처 결과가 비정상(균일 픽셀·실패)일 때의 안내 문구만 준비한다 — macOS판 verify_pixels의 균일 픽셀 검사 로직을 인메모리 버퍼용으로 추출·공용화하고 메시지는 Windows용으로 교체(현행 함수는 파일 경로 입력 + TCC 전용 문구라 그대로 재사용은 안 됨).
탈출 조건 (macOS판 "Electron 2d 룰"을 이 트랙에서 대체하는 룰): Tauri 웹뷰 오버레이의 엣지 케이스(표시 지연·z-order·Win11 taskbar 겹침 tauri-apps/tauri#7328 등)로 2 active-day 이상 소모되면, 전면 전환이 아니라 오버레이 창만 native Win32 layered window(Rust 직접 구현)로 국소 교체한다 — 캡처 엔진·어노테이터·파이프라인은 영향 없음. 그래도 막히면 최후 폴백은 ② MSIX + Snipping Tool 프로토콜 — 단 발동 시 §8의 NSIS 배포 전략이 MSIX로 재편되는 비용(W4의 Store 트랙 선행)까지 감수하는 결정임을 명시해 둔다. 이 결정을 미루지 말 것.

6. 이미지·좌표 정책 (Windows) — 그리고 macOS판에 주는 숙제

쉽게 말하면: Windows는 화면 확대 배율이 125%, 150%처럼 어중간해서 "반으로 줄이면 딱 맞는" macOS식 계산이 안 통해요. 대신 AI가 이미지를 절대 다시 줄이지 않도록, AI 공식 계산법으로 정확한 크기를 미리 맞춰서 저장해요. 조사 중에 지금 macOS 버전 계산에도 빈틈이 있다는 걸 발견했어요.

6.1 캡처 픽셀 공간 — 물리 픽셀, 실측 배율

PMv2 프로세스에서 xcap/DXGI 캡처는 물리 픽셀 프레임을 준다. 모니터별 배율은 pHYs 추정 없이 GetDpiForMonitor(Tauri scale_factor())로 캡처 시점에 정확히 안다 — macOS판보다 오히려 견고하다. pHYs 청크는 Windows 생태계에서 배율 감지 채널로 신뢰할 수 없으므로(Snipping Tool도 96dpi 고정 관례) 기록하지 않고 파싱도 하지 않는다 — 현행 파이프라인(캔버스 → PNG 인코드)도 기록하지 않으므로 현상 유지다.

6.2 다운스케일 정책 개정 — "장변 1568" 단일 규칙은 불충분했다

리서치 발견 (이 계획서에서 가장 중요한 기술 변경): Anthropic 비전의 리사이즈는 "장변 ≤ 1568px" 하나가 아니라 장변 제한 + 비주얼 토큰 제한(28×28px 패치당 1토큰)의 이중 제약이다. 표준 티어는 1568px/1568토큰 — 16:9 1568×882조차 56×32=1792토큰이라 모델이 ~1456×819로 재축소한다. 즉 기존 규칙만으로는 "모델이 보는 픽셀 = 텍스트 좌표"(불변식 3의 목적)가 화면비에 따라 깨진다. 공식 문서(vision-coordinates)가 정확한 resized_size() 참조 구현과 함께 "사전 리사이즈로 1:1을 맞추라"고 권고한다.
  • Windows판은 처음부터 공식 resized_size() 이중 제약으로 저장 크기를 결정한다 (참조 구현 이식, Rust/TS 수십 줄). 한계 이하 크기는 네이티브 보존, 업스케일 금지·PNG 전용은 그대로.
  • 다운스케일 프로필: v1 범위는 범용(1568px/1568토큰 — 어떤 티어 모델에서도 1:1 보장, 불변식 3의 현행 문언 "장변 ≤1568" 안에서 동작) 고정. 고해상도 프로필(2576px/4784토큰 — Claude Code의 현행 모델 티어 전제, 픽셀 보존 최대)은 장변이 1568을 넘는 저장을 허용하므로 불변식 3 문언 개정(§12 결정 4)이 승인되기 전까지 설계 예비(W4)로만 둔다.
  • 분수 배율 축소의 1px 디테일 열화(정수 1/2보다 비예측적)는 불가피하므로: 리샘플 필터는 Lanczos3(또는 CatmullRom) 지정, 그리고 "정밀 지목은 영역 캡처(네이티브 보존 구간)로" 유도하는 UX 문구를 유지한다 — 제품 스위트스팟이 영역 캡처인 것은 macOS판과 동일.
  • macOS 백포트 후보: 현행 macOS판도 같은 이슈를 갖는다 (16:10 Retina 전체 화면 2880×1800 → 1440×900 = 1716토큰 > 1568 → 표준 티어에서 재축소). Phase 0/2/3 검증은 고해상도 티어 모델(Claude Code)에서 수행돼 통과한 것으로 해석된다. 백포트 여부·시점은 §12 미해결 질문 — 이 트랙에서 조용히 섞지 말고 별도 결정으로.

6.4 scale: 줄 — 값 채우기 정책 (문법 무변경)

Windows에서는 "1 image px = 1 CSS px"가 항상 성립하지 않는다. scale: 줄은 동결된 문법 방향(N image px = 1 CSS px, 계수는 image px 쪽)을 그대로 유지하되 실측 계수를 기록하는 정보성 필드로 쓴다. 계수 정의는 N = OS 배율(scale factor) × 저장 축소율 — 예: §6.3 표의 "1200×900 CSS 창 @150%, 범용 저장 0.706" 시나리오라면 N = 1.5 × 0.706 = 1.06, 즉 scale: 1.06 image px = 1 CSS px. 에이전트의 좌표 해석은 계속 image px만 사용한다(불변식 2). 이는 필드 값의 정책이지 문법 변경이 아니므로 스펙 동결과 충돌하지 않는다 — 소수 계수 표기를 에이전트가 오해석하지 않는지, 괄호 주석 병기가 v1 파서와 호환되는지는 W0 E2E 확인 항목이며, 문법 확장이 필요해지면 v1.1 제안으로만 처리한다.

6.5 멀티모니터 — "모니터 로컬 물리 픽셀" 원칙

  • 오버레이는 모니터당 1개. Windows에서 창 1개는 DPI 1개만 갖는다 — 여러 mixed-DPI 모니터에 걸친 단일 오버레이는 구조적으로 부정확하다 (ShareX가 같은 함정으로 다수의 재발성 버그 보유: #8002, #5412 등).
  • 크롭 산술은 모니터 로컬 물리 좌표로만. 가상 데스크톱 전역 좌표(primary 원점, 음수 가능)는 모니터 식별에만 쓰고 픽셀 계산에 쓰지 않는다.
  • 선택 영역은 단일 모니터 내로 제한 (v1). 모니터 경계를 넘는 드래그는 mixed-DPI 스티칭 문제를 만들므로 W4 백로그로 보낸다 — macOS판도 단일 화면 선택이 기본 시나리오였다.
  • 분수 배율에서 CSS px × scale_factor의 반올림 ±1px 드리프트는 실기기 E2E(125%/150%)로 floor/round 규칙을 확정한다 (W2 완료 기준에 포함).

7. CapNote 전달 경로 (Windows) — 경로 스타일과 지원 매트릭스

쉽게 말하면: Windows에서는 AI 터미널이 두 가지 방식(진짜 Windows용 / 리눅스 흉내 내는 WSL용)으로 돌아요. 같은 파일이라도 두 방식이 부르는 주소가 달라서, 편지에 어떤 주소를 적을지 설정 하나로 고를 수 있게 해요.

7.1 저장 위치 — %USERPROFILE%\.capnote\ 유지

Claude Code 자신이 %USERPROFILE%\.claude를 쓰는 것을 포함해, 프로필 루트 dot-폴더는 Windows 개발자 도구의 확립된 관례다(.ssh, .gitconfig, .cargo …). macOS ~/.capnote와 1:1 일관성이 있고, WSL에서 /mnt/c/Users/<name>/.capnote로 예측 가능하며, OneDrive Known Folder Move(Documents/Pictures 리다이렉트)의 영향권 밖이다. %LOCALAPPDATA%는 "캡처는 앱 캐시가 아니라 사용자 데이터"라는 제품 성격에 안 맞아 기각 — 경로는 지금처럼 설정으로 변경 가능하게 유지한다. 구현은 settings.rs의 ~ 확장이 $HOME만 보는 부분을 USERPROFILE 폴백으로 확장하면 된다.

7.2 경로 스타일 설정 — 경로 전달을 위한 신규 설정 (신규 사용자 설정은 pathStyle과 §6.2 다운스케일 프로필 2개)

캡처 앱은 소비자 터미널이 네이티브인지 WSL인지 알 수 없으므로 자동 감지는 불가능하다. 설정 1개(pathStyle)로 해결한다:

모드image: 줄에 실리는 경로대상
windows (기본)C:\Users\name\.capnote\2026-07-03-101512.png네이티브 Claude Code (PowerShell·CMD·Git Bash)
wsl/mnt/c/Users/name/.capnote/2026-07-03-101512.pngWSL2의 Claude Code
  • 경로는 CapNote v1 문법에서 "필드 값"일 뿐이므로 스펙 동결 위반이 아니다. 두 경로 병기 같은 문법 확장은 기각(v1 동결) — 필요 실증 시 v1.1 제안으로.
  • 네이티브 모드의 구분자(백슬래시 vs 슬래시 C:/Users/...)는 W0 E2E로 확정한다. 잠정 기본은 백슬래시(OS canonical) — 단 Claude Code의 permission glob 매칭은 백슬래시에서 깨지는 공식 이슈(anthropics/claude-code#30736)가 있으므로, Read 경로에서도 이상 거동이 보이면 슬래시로 전환한다 (공식 문서 스스로 "Windows에서도 슬래시를 쓰라"고 안내하는 지점이 있음).
  • 온보딩(첫 실행)에서 1회 질문 + 설정 창에서 전환 가능하게.

8. 기술 선택 (Windows 셸·배포)

쉽게 말하면: 골격(Tauri)은 그대로 쓸 수 있다는 걸 확인했어요. 설치 파일 만들기와 "서명" 문제(서명이 없으면 Windows가 처음에 경고창을 띄워요)만 Windows만의 새 숙제예요.

플러그인 패리티 — 재사용 + 최우선 스모크 1건

  • global-shortcut · clipboard-manager · single-instance 3종 모두 Windows 데스크톱 공식 지원. 버전 핀(=) 유지.
  • "등록은 성공하는데 콜백이 발화하지 않는" Windows 리포트(tauri-apps/plugins-workspace#2646)는 2025-04 종결 — 원인은 플러그인 회귀가 아니라 제보 환경(bun lockfile 손상)으로 판명. 즉 알려진 미해결 Windows 결함은 없다. 그래도 단축키는 제품 진입점이므로 W0에서 통상 스모크(콜백 발화 확인)를 수행하고, 만에 하나를 대비한 보험으로 백엔드인 global-hotkey 크레이트 직접 사용 경로와 트레이 메뉴 폴백(캡처 버튼, macOS판 그대로)을 유지한다.
  • 트레이: show_menu_on_left_click의 Windows 지원은 Tauri 2.2.0+ — 현재 의존이 tauri = "2"이므로 충족. 트레이 아이콘은 32bit RGBA 정사각 PNG로 준비(라이트/다크 각각), icon_as_template 호출은 macOS cfg로 격리.
  • autostart(선택 — 수요 시): tauri-plugin-autostart = HKCU Run 키. "재부팅 후 엔트리 소실" 이슈(tauri-apps/plugins-workspace#771) 재현 확인을 QA 1항목으로.

포커스 복귀 — macOS보다 단순

단축키 발화 시점에 GetForegroundWindow()로 HWND를 기억 → 커밋/ESC 후 IsWindow 검사 → (최소화면 SW_RESTORE) → SetForegroundWindow(). 커밋 시점에는 우리 앱이 포그라운드 프로세스이므로 MS 공식 허용 조건("호출 프로세스가 포그라운드 프로세스")에 정확히 부합한다 — AttachThreadInput 류 해킹은 v1 범위에서 제외하고 리스크로만 관리. macos.rs 대응 windows.rs 수십 줄 (windows 크레이트, Win32_UI_WindowsAndMessaging feature).

11. 주요 리스크 9건

쉽게 말하면: 미리 알아낸 함정 목록이에요. macOS 때의 함정 8개 중 상당수는 사라졌고(권한 문제 등), 대신 Windows만의 새 함정(직접 만드는 캡처 화면, 어중간한 배율)이 생겼어요.

리스크영향대응
1. 자체 오버레이 품질 (macOS에선 OS가 공짜로 주던 것) 표시 지연(WebView2 cold start)·z-order·Win11 taskbar 겹침(tauri-apps/tauri#7328)·풀커버 창의 하부 비디오 일시정지(tauri-apps/tauri#7401) — 캡처 UX 전체의 신뢰가 걸림 프리즈 프레임 방식(occlusion 무관 가능성 — W0 확인) + 숨김 오버레이 사전 생성·재사용(<300ms 목표) + 2 active-day 탈출 룰: 오버레이만 native Win32 layered window로 국소 교체 (§5)
2. 전역 단축키의 Windows 신뢰성 콜백 미발화 시 제품 진입점 마비. 단 과거 리포트(tauri-apps/plugins-workspace#2646)는 2025-04에 제보 환경 원인으로 종결 — 알려진 미해결 결함은 없음 (보험 성격의 리스크) W0 통상 스모크 → 이상 시 global-hotkey 크레이트 직접 사용 → 트레이 메뉴 폴백 상시 유지. PrtScn·OneDrive 가로채기와의 충돌은 기본 키(Alt+Shift+C) 유지로 회피
3. mixed-DPI 멀티모니터 좌표 매핑 모니터마다 배율이 다르면 마커가 엉뚱한 곳을 지목 → 신뢰 붕괴 (ShareX 동종 재발성 버그 다수) 모니터당 오버레이 1개 + 모니터 로컬 물리 좌표 산술 + 크로스 모니터 드래그 v1 금지 + Rust 단독 지오메트리(웹뷰 화면 API 금지) — §6.5 원칙으로 원천 회피. 100%+150% 실측이 W3 완료 기준
4. 분수 배율 다운스케일이 1px 디테일 손상 125%/150%에서 축소 배율이 0.38~0.76 — 보고 대상(1px 보더)이 안티에일리어싱으로 뭉개질 수 있음 (macOS 리스크 #3의 악화판) 영역 캡처(네이티브 보존 구간) 유도 UX + Lanczos3 리샘플 + 고해상도 프로필 옵션. 전체 화면 캡처의 잔존 리스크는 인지하고 감수
5. Anthropic 리사이즈 이중 제약 (신규 발견) "장변 1568" 단일 규칙으로는 화면비에 따라 모델이 재축소 → 좌표 1:1 깨짐. macOS 현행 구현도 동일 이슈 내포 Windows판은 공식 resized_size()로 처음부터 구현. macOS 백포트는 별도 결정(§12) — 이 트랙에 섞지 않음. 외부 규칙 변경 감시 대상(리스크 9와 결합)

사용자 결정 5건 (차단 수준 표기)

  1. [W0 차단] Windows 트랙 착수 여부 자체 — HANDOFF.md §4는 크로스플랫폼을 "필요 실증 시에만" 착수하는 백로그로 게이트한다. 이 계획서는 착수 결정이 아니라 착수 준비다 — 실수요(본인의 Windows 사용 계획 또는 초기 사용자 수요)를 확인하고 착수를 승인하는 결정이 선행되어야 한다.
  2. [W0 차단] Windows 검증 기기 확보 방법 — 실기 Windows 머신(권장: 125%/150% 배율 노트북 + 외부 모니터로 mixed-DPI 재현 가능) vs Parallels VM만으로 시작(최종 검증만 실기 대여).
  3. [W0 착수 전 권장] 1차 소비 환경 — 본인/초기 사용자의 Claude Code가 네이티브인지 WSL인지 → pathStyle 기본값과 W0 E2E 우선순위에 반영. 미정이면 W0에서 양쪽 모두 E2E.
  4. [W1 전까지] 최소 지원 OS 라인 — Windows 10 21H2+(제안) vs Windows 11 전용. Win10 유지 시 WGC 노란 테두리 제약 때문에 GDI 경로 고정이 사실상 확정된다.
  5. [W2 전까지 · 선택] 불변식 3 문언 개정 — "장변 ≤1568px 단일 규칙"을 "공식 이중 제약 resized_size() 기준"으로 개정할지(§6.2). 개정 승인 시 CLAUDE.md·plan.html의 해당 문구·수치를 함께 갱신하고 고해상도 프로필이 해금된다. 미승인이어도 v1(범용 프로필)은 현행 문언 안에서 진행 가능.
