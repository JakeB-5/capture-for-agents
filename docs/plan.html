1. 이 문서는?

쉽게 말하면: 우리가 만들 도구의 "설계도"예요. 무엇을, 왜, 어떤 순서로 만들지 한 장에 다 담았어요.

이 문서는 Capture for Agents의 확정된 설계 브리프를 작업계획서 형태로 정리한 것이다. 아직 코드는 한 줄도 없다(그린필드). 그래서 지금이 가장 싸게 방향을 고칠 수 있는 시점이고, 이 문서가 그 기준점이 된다.

읽는 순서는 위에서 아래로: 무엇을 만들고(§2), 왜 필요한지(§3), 결과물이 에이전트에게 어떻게 전달되는지(§4~5), 사용자는 뭘 보게 되는지(§6), 무엇으로 만들지(§7), 어떤 순서로 며칠 만에 만들지(§8~9), 무엇이 위험한지(§10), 그리고 내일 당장 뭘 할지(§11).

문서 언어 정책: 산문은 한국어, 코드·CLI 명령·포맷 키워드는 영어. 수치·경로·단축키(CapNote v1, ⌥⇧C, ~/.capnote/, 1568px, 14일/500개)는 모든 문서에서 동일하게 유지한다.

2. 무엇을 만드나

쉽게 말하면: 스크린샷에 번호 스티커를 붙여서 AI에게 "여기!"라고 알려주는 도구예요. 찍고, 콕 찍어 표시하고, 붙여넣기 한 번이면 끝.

터미널에서 일하는 AI 코딩 에이전트(Claude Code 등)는 "버튼이 좀 이상해요" 같은 말만으로는 화면의 정확히 어디가 문제인지 알기 어렵다. 이 도구는 화면을 캡처하고, 그 위에 번호 마커·사각형·화살표와 짧은 설명을 붙인 뒤, ⌘V 한 번으로 에이전트에게 "정확히 어디를 어떻게 고칠지"를 전달한다.

목표 체감 속도: 마커 1개짜리 피드백 약 5초, 3개짜리 약 10초.

핵심 설계 불변식 5개

아래 다섯 문장은 이 프로젝트의 "절대 규칙"이다. 모든 설계·구현·문서가 이것과 모순되면 안 된다.

  1. 클립보드는 텍스트 전용. 이미지는 클립보드에 넣지 않는다. 번인된 PNG는 파일로 저장하고 절대 경로를 텍스트에 포함 → 에이전트가 Read 도구로 직접 읽는다.
  2. 좌표계는 단 하나: "저장된 최종 이미지의 픽셀"(원점 좌상단). 헤더에 size(실측 WxH)를 선언하고, 원본 Retina 좌표는 절대 노출하지 않는다.
  3. 이미지는 장변 ≤ 1568px PNG. Retina @2x는 1/2로 축소, 이미 작은 크롭은 네이티브 유지. JPEG 금지, 업스케일 금지.
  4. 번인(burn-in)은 필수, 단 다운스케일 후 최종 해상도에서 렌더링. 번호 배지는 대상을 가리지 않게 8~12px 오프셋+리더 라인. 노트 본문은 번인하지 않는다.
  5. 마커·사각형·화살표가 하나의 자동 증가 번호 시퀀스를 공유. 이 번호가 이미지와 텍스트를 잇는 join key다.

3. 왜 필요한가 — Figma 스토리

쉽게 말하면: 말로 "저기 좀 이상해"라고 하면 아무도 못 알아들어요. 사진에 동그라미 치고 번호를 붙여서 "1번은 이것, 2번은 저것"이라고 해야 정확히 전달돼요.

대표 시나리오는 이렇다. Figma 시안을 코드로 옮겼는데, 눈으로 비교해 보니 디테일이 미반영됐다 — 카드에 1px 보더가 빠졌고, 마진이 절반이고, 아이콘이 작다. 이런 것을 말로 설명하면 에이전트는 "어떤 카드? 어느 방향 마진?"부터 헤맨다. 이 도구로는 캡처 → 번호 마커/사각형/화살표 + 한 줄 설명 → ⌘V, 이 세 걸음이면 "정확히 어디를 어떻게"가 전달된다.

왜 이미지를 클립보드에 안 넣나 (불변식 1의 근거)

여기에 함정이 하나 있다. Claude Code에서 이미지 붙여넣기는 macOS에서 ⌘V가 아니라 Ctrl+V다. 사용자가 습관대로 ⌘V를 누르면 이미지는 조용히 사라진다. 게다가 이미지만 붙여넣으면 "이 그림으로 뭘 하라는 건지"라는 의미 정보가 없다.

그래서 클립보드에는 텍스트만 넣는다. 텍스트 안에 이미지 파일의 절대 경로가 들어 있으므로, ⌘V 한 번으로 시각 채널(에이전트가 경로를 Read)과 의미 채널(번호·좌표·노트)이 동시에 도착한다. 붙여넣기 방식의 함정을 아예 우회하는 설계다.

4. 어떻게 전달되나 — CapNote v1

쉽게 말하면: 편지 한 통에 "사진이 보관된 위치"와 "사진 속 번호별 설명"을 같이 적어 보내는 방식이에요. 받는 쪽은 편지를 읽고, 적힌 위치에서 사진을 꺼내 보고, 번호로 둘을 맞춰 봐요.

CapNote v1은 클립보드에 실리는 페이로드 포맷이다. ```capnote v1 펜스로 감싼 UTF-8 플레인 텍스트로, 정규식 한 줄로 기계 파싱이 가능하면서 사람이 그대로 읽힌다. 비전(이미지 인식)이 없는 모델도 좌표+노트만으로 동작할 수 있다.

5. 이미지·좌표 정책

쉽게 말하면: 지도를 반으로 줄였으면 보물 위치도 줄인 지도 기준으로 적어야 해요. 우리는 헷갈리지 않게, 처음부터 "줄인 지도" 하나에만 좌표를 적어요.

Retina 디스플레이는 화면 1포인트를 물리 픽셀 2개(@2x)로 그린다. 캡처 원본은 2배로 크고, 여기 좌표와 저장본 좌표가 섞이면 마커가 엉뚱한 곳을 가리킨다. 그래서 좌표계는 단 하나 — 저장된 최종 이미지의 픽셀(원점 좌상단)만 쓴다(불변식 2).

또 하나의 근거: Anthropic 비전 API는 장변이 1568px를 넘는 이미지를 자체적으로 리사이즈한다. 저장본을 처음부터 장변 ≤ 1568px로 맞추면 API가 이미지를 건드리지 않으므로, 모델이 실제로 보는 픽셀과 텍스트에 적힌 좌표 공간이 정확히 1:1이 된다(불변식 3).

번인 규칙 (불변식 4)

  • 번인은 다운스케일 후 최종 해상도에서 렌더링한다. 먼저 그리고 줄이면 배지가 흐려진다.
  • 번호 배지는 대상 픽셀을 가리지 않게 8~12px 오프셋 + 리더 라인으로 배치한다.
  • rect 주석은 점선(dashed) + 대상 바깥 2px 아웃셋으로 그린다 — 보더 누락을 지적할 때 주석 사각형이 실제 보더처럼 보이는 문제를 막는다. (Phase 0 검증에서 비전 에이전트 3/3이 지적)
  • point 주석은 채운 점 대신 링(비채움 원)으로 그린다 — 지목 대상(작은 아이콘 등)을 가리지 않게.
  • 노트 본문 텍스트는 이미지에 번인하지 않는다 — 그건 텍스트 채널의 일이다. 이미지에는 번호와 도형만 남긴다.

저장과 보존

  • 저장 위치: ~/.capnote/YYYY-MM-DD-HHMMSS.png. 경로는 설정 가능 — 샌드박스 에이전트가 홈 밖 경로를 못 읽는 경우에 대비한다.
  • 자동 정리(GC): 앱 시작 시 14일 경과 또는 500개 초과분을 삭제한다.

6. 어노테이션 창 설계

쉽게 말하면: 사진을 찍자마자 열리는 창에서 "콕 찍고 → 한 줄 쓰고 → Enter" — 이 세 동작만 반복하면 끝나요. 도구를 고르러 마우스를 옮길 필요가 없어요.

캡처 직후 어노테이션 창이 즉시 열린다(always-on-top, 이미지 크기). 핵심은 "클릭→타이핑→Enter" 단일 루프다: 어노테이션을 놓는 순간 인라인 노트 입력이 자동 포커스되고, 타이핑 후 Enter로 확정하면(빈 채로 Enter = 노트 생략) 캔버스로 복귀해 바로 다음 클릭이 가능하다.

스마트 툴이 기본 도구다: 클릭은 번호 마커, 4px 이상 드래그는 사각형, Shift+드래그(또는 A)는 화살표로 자동 판별된다. 1/2/3 키로 명시적 도구 전환도 가능하다.

7. 기술 선택

쉽게 말하면: 이미 macOS 안에 들어 있는 부품(스크린샷 명령어)을 최대한 빌려 쓰고, 우리는 그 위에 얇은 껍데기와 그림 그리는 화면만 만들어요. 바퀴를 다시 발명하지 않아요.

스택은 Tauri v2 메뉴바 상주 앱이다. 제품의 95%인 어노테이션 UI는 TypeScript + Canvas 2D로 만들고, Rust는 얇은 셸에 그친다 — 공식 플러그인(global-shortcut, clipboard-manager)과 screencapture 프로세스 스폰 수십 줄. 결과: 바이너리 ~10MB, 상주 메모리 ~30MB, 콜드 스타트 없음.

캡처 방식: 자체 오버레이 대신 OS 내장 명령

/usr/sbin/screencapture -i -x -o -t png <tmpfile>을 스폰한다. -i가 드래그 선택 + Space 키 창 선택 토글 + ESC 취소(파일 미생성으로 감지)를 공짜로 제공하므로 자체 캡처 오버레이가 필요 없다. -x는 셔터음 제거, -o는 창 그림자 제거이고, -J window로 창 모드 시작 변형도 가능하다.

  • dev 모드에서는 권한이 터미널/IDE에 귀속되는 점에 주의. macOS 15+의 주기적 재승인 프롬프트는 리스크로 관리한다(§10).

9. 일정 산정

쉽게 말하면: "몇 명이 몇 달 걸릴까"가 아니라, 실제로 재어 둔 "내 하루 속도"로 계산해요. 다만 아무리 서둘러도 줄지 않는 일(권한 승인 기다리기, 실기기 테스트 같은)이 최소 기간을 정해요.

이 프로젝트는 1인 + AI 오케스트레이션 개발이며, 산정은 업계 평균(N인 팀 × M개월)이 아니라 실측 개인 속도(active-day 기준)를 적용한다. 사용한 가정은 아래 표에 전부 명시한다.

가정 / 단계값비고
산정 기준 1인 + AI 오케스트레이션, 실측 개인 속도(active-day) COCOMO·"N인 팀 × M개월" 방식 미적용
관례적 추정 앵커 이런 도구의 폴리시드 MVP ≈ 2~3 eng-month 변환의 출발점으로만 사용
작업 믹스 압축형 ~40% / 표준형 ~40% / 직렬꼬리 ~20% 압축형: 스캐폴드·캔버스 도구·문서 / 표준형: 어노테이션 UX·포맷·클립보드 / 직렬꼬리: TCC 권한 거동, 포커스 복귀, 터미널 붙여넣기 실측, Retina/멀티모니터 QA 루프
레버리지 (AI 가속 배수) 압축형 45 · 표준형 11 · 직렬꼬리 5 (블렌디드) + 런타임 QA 루프 버퍼
결과 약 6~9 active-day ≈ 0.3~0.5 달력개월 Phase 합계 5.5~8.5d와 정합
왜 하한이 존재하나: 직렬꼬리(권한 거동·포커스 복귀·터미널 인터롭·좌표 정확성 QA)는 병렬화로 줄지 않는다 — 실기기에서 순서대로 확인해야 하는 일이기 때문. 이것이 달력 기간의 하한을 결정하며, Phase 0/1이 바로 이 리스크를 최전방에서 검증하도록 로드맵이 짜여 있다.

10. 주요 리스크 8건

쉽게 말하면: 미리 알고 있는 함정 목록이에요. 함정의 위치를 알면 밟기 전에 피하거나, 밟았을 때 빨리 빠져나올 수 있어요.

리스크영향대응
1. TCC 화면 기록 권한 거동 dev 빌드 서명 변경 시 권한 리셋, macOS 15+ 주기적 재승인, 미승인 시 창이 누락된 이미지가 조용히 반환 Phase 1 실기기 검증 + 온보딩에서 테스트 캡처의 픽셀 검증 + 안정적 자가서명 인증서
2. 좌표 공간 불일치 (Retina/멀티모니터) 마커가 엉뚱한 위치를 지목 → 신뢰 붕괴 좌표는 오직 저장본 픽셀, 크기는 PNG 실측값 — 불변식으로 고정 (§5)
3. 다운스케일이 1px 디테일을 삭제 보고 대상(1px 보더 등) 자체가 이미지에서 사라질 수 있음 작은 크롭은 @2x 네이티브 유지로 완화. 전체 창 캡처에선 리스크 잔존을 인지
4. 에이전트가 hint 무시 / 이미지 px를 CSS px로 오인 좌표를 잘못 환산해 엉뚱한 코드 수정 hint 문구에 명시 + Phase 3 지목 정확도 평가로 튜닝. 완전 제거는 불가함을 전제
5. 번인 배지의 겹침·가림 밀집 어노테이션에서 배지가 서로 겹치거나 대상 픽셀을 가림 8~12px 오프셋 + 리더 라인으로 완화. 충돌 회피 배치는 Phase 3
6. 터미널 멀티라인 붙여넣기 엣지 bracketed paste가 없는 셸에서 멀티라인이 줄 단위로 분해될 수 있음 Claude Code는 문제없음. iTerm2/Terminal/VS Code 3종 실측 + 노트 소프트 리밋
7. Tauri v2 플러그인의 macOS 신버전 회귀 단축키·클립보드 등 셸 기능 마비 버전 핀 + 트레이 메뉴 폴백 + Electron 탈출 조건(2 active-day 룰, §7)
8. 외부 가정 결합 Anthropic 비전 1568px 규칙, Claude Code의 Ctrl+V/경로 Read 거동이 바뀌면 설계 전제가 흔들림 거동 변경 감지 시 정책 재검토 — 관리 항목으로 명시

11. 미해결 질문과 첫 행동

쉽게 말하면: 아직 답을 모르는 질문들과, 그 답을 알아내기 위해 내일 당장 할 실험이에요. 앱을 만들기 전에 종이 모형으로 먼저 실험해요.

미해결 질문

  • hint의 최적 문구는 무엇인가? (Phase 0에서 초안 검증, Phase 3에서 정확도 평가로 튜닝)
  • 샌드박스 에이전트가 ~/.capnote/를 못 읽는 환경이 실제로 얼마나 되나? 경로 설정 옵션으로 충분한가?
  • 밀집 어노테이션에서 배지 충돌 회피 배치가 어느 수준까지 필요한가? (Phase 3 판단)
  • 클립보드 이미지 동시 탑재 옵션(Phase 4 백로그)에 실수요가 있는가?
  • macOS 15+ 재승인 프롬프트가 실사용에서 얼마나 자주 뜨는가?

첫 행동 — Phase 0 스파이크 체크리스트 (0.5d)

코드 한 줄 없이, 가장 큰 가설("에이전트가 CapNote를 정확히 해석한다")을 오늘 검증할 수 있다.

  1. screencapture -i -x -o -t png로 샘플 화면(카드 컴포넌트 류)을 수동 캡처한다.
  2. 스크립트(sips 등)로 1/2 다운스케일하고 장변 ≤ 1568px, PNG 유지를 확인한다.
  3. 스로어웨이 HTML 캔버스에서 point/rect/arrow 3종과 번호 배지(오프셋+리더)를 번인하고 좌표를 기록한다.
  4. 표준 예시(§4) 형식대로 CapNote v1 블록을 수동 작성한다.
  5. 클립보드에 텍스트만 복사해 실제 Claude Code에 ⌘V로 붙여넣는다.
  6. 에이전트가 image: 경로를 Read하는지, [1][2][3] 마커 3종을 각각 정확히 지목하는지 확인한다.
  7. 비전을 쓰지 않는 조건(좌표+노트만)에서도 유효하게 동작하는지 확인한다.
  8. 결과를 바탕으로 hint 문구와 문법을 확정하고 CapNote v1 스펙을 동결한다 → Phase 1 착수. ✅ 2026-07-02 완료 — 블라인드 에이전트 6개로 검증, 마커 지목 9/9 · 파싱 무오류. 결과와 동결 수정 4건: phase0-verification.md
